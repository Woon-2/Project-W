# DEVLOG

## 2026-06-22 — 클라이언트-서버 시간 동기화 개선

### 문제

온라인 플레이에서 룸 서버와 클라이언트가 서로 다른 PC에서 실행될 때 특정 플레이어의 스킬 공격이 적중하지 않는 문제가 발생했다. 클라이언트와 서버가 각자의 `high_resolution_clock` 값을 직접 비교하고 있었기 때문에 PC마다 다른 시계 기준점이 지연으로 계산되었고, 서버의 스킬 경과 시간이 최대값인 `65535ms`로 포화되었다.

`SwordSlash`처럼 전체 지속 시간이 400ms인 스킬은 시작과 동시에 모든 히트박스 생성·삭제 이벤트가 처리된 후 종료되었다. 이 때문에 스킬 시작 패킷과 히트박스 생성 로그는 남지만 실제 충돌 검사 시점에는 활성 히트박스가 존재하지 않았다.

### 시간 동기화

- 프로토콜에 `C_TimeSync`와 `S_TimeSync`를 추가했다.
- 클라이언트 송신 시각(t0), 서버 수신 시각(t1), 서버 송신 시각(t2), 클라이언트 수신 시각(t3)을 이용해 NTP 방식으로 RTT와 서버 시계 오프셋을 계산한다.
- 네트워크 판정용 시계는 벽시계 변경의 영향을 받지 않는 `steady_clock`을 사용한다.
- 룸 입장 직후 동기화하고 이후 10초마다 오프셋을 갱신한다.
- `CAttackPacket`과 `CSkillStartPacket`은 클라이언트 로컬 시각 대신 동기화된 서버 추정 시각인 `actionServerMs`를 전송한다.

초기 구현에서는 `C_TimeSync`가 사용자 영역의 송신 대기 큐에 들어갈 때 t0를 기록했다. 실제 `WSASend` 호출까지 최대 한 프레임의 대기 시간이 포함되면서 오프셋이 미래 방향으로 편향될 수 있었다. 이를 막기 위해 타임 동기화 패킷에 한해서 실제 `WSASend` 직전에 `clientSendMs`를 다시 기록하도록 개선했다. Overlapped I/O 완료 시각은 실제 송신 시작 시각이 아니므로 동기화 기준으로 사용하지 않는다.

### 서버 검증과 권위

- 서버는 `actionServerMs`를 판정 결과가 아닌 지연 보정 힌트로만 사용한다.
- 인정하는 지연 보정 범위는 최대 250ms다.
- 미동기화 값, 서버보다 미래인 값, 250ms보다 오래된 값은 서버 수신 시각으로 대체한다.
- 검증된 값만 스킬 타임라인의 `initialElapsed`와 기존 평타의 NPC 위치 되감기에 사용한다.
- 히트박스 생성, 충돌 검사, 대상·진영 검증, 피해량 및 HP 변경은 계속 서버에서 결정한다.

따라서 비정상 타임스탬프가 들어와도 공격 판정이 제거되거나 스킬이 무제한으로 앞당겨지지 않는다. 검증 실패 시 지연 보정만 생략하고 현재 서버 시각 기준으로 정상 판정한다.

### 검증

- `RoomServer Release x64` 빌드 성공
- `client Release x64` 빌드 성공
- 정상 동기화 시 서버의 `[DIAG skillTime]` 로그에서 `valid=1`, `elapsedMs=0~250` 범위인지 확인한다.
- `valid=0`이어도 서버 수신 시각으로 안전하게 폴백되어 공격 판정은 유지된다.
- 현장 검증이 끝날 때까지 `[TimeSync]`, `[DIAG C_SkillStart SEND]`, `[DIAG skillTime]` 등 관련 진단 로그를 유지한다.
