01 · CURRENT IMPLEMENTATION

현재 프로젝트에서 확인된 기반

코드에 이미 있는 기능은 상당히 유리하지만, “재사용 가능”과 “그대로 호출 가능”은 다르다. 아래 차이가 난이도를 좌우한다.

HDR + Bloom 경로가 이미 존재

EnergyOrbPipeline은 deferred lighting 이후 SceneColorHDR에 가산 렌더되고, 블룸 전에 실행된다. 발광 길 안내에 이상적인 위치다.

에너지 오브는 범용 구체가 아님

몬스터의 Position/BoneIndices/BoneWeights/UV와 사망 포즈 팔레트를 요구하고, 각 정점을 구체 내부로 모핑한다. 단순 경로 포인트에는 입력 구조가 과하다.

standalone에는 오브 시스템 연결이 없음

카메라 데이터와 GPU 파이프라인은 공통이지만 EnergyOrbSystem의 update/submit은 현재 online 쪽에만 연결되어 있다. standalone 확인을 위한 게임 레이어 연결이 필요하다.

지형 높이·법선 질의 가능

TerrainChunkManager::heightAtWorld와 normalAtWorld가 있어 화살표·리본·구체를 지형에 맞출 수 있다.

Unity 좌표를 직접 사용 중

TerrainExtractor의 marker/zone/scatter가 Unity 월드 좌표와 quaternion을 그대로 기록한다. 경로 데이터도 동일한 규칙을 따르면 별도 축 변환이 필요 없다.

JSON 로더 기반이 충분함

simpleJson과 여러 실제 import 사례가 있다. 경로는 서버 공용 chunks_index.bin보다 별도 versioned JSON이 반복 작업에 유리하다.

04 · UNITY AUTHORING & EXPORT

Unity에서 경로를 만들고 가져오는 방법

권장안은 “Unity에서 의미 있는 곡선을 만들고, 엔진에서는 일정 거리로 재샘플링해 표시”하는 구조다. 점을 지나치게 많이 export하지 않아도 연출 밀도를 자유롭게 바꿀 수 있다.

1. 경로 제작

GuidancePath 컴포넌트 아래에 waypoint를 두거나 Unity Splines를 사용한다. 시작/도착만 지정하고 NavMesh 경로를 bake하는 방식도 선택 가능하다.

→
2. Editor Export

곡선을 0.5~1.0m 간격으로 샘플링하고 ground raycast 또는 NavMesh 위치 보정 후 guidance_paths.json으로 저장한다.

→
3. Client Import

simpleJson으로 로드한 뒤 표시 방식별 간격으로 다시 샘플링한다. 같은 데이터로 구체·화살표·리본을 교체할 수 있다.

권장 제작 모드

  1. 수동 spline/waypoint: 연출자가 길의 모양과 우회 구간을 정확히 통제. 기본 권장.
  2. NavMesh bake: 시작·목적지 사이 보행 가능 경로를 자동 생성. 지형/장애물 변경 시 재생성이 편함.
  3. 혼합: 주요 checkpoint는 수동 지정하고 각 구간만 NavMesh로 연결. 제작 안정성이 가장 높음.

왜 별도 JSON인가

  • 길 안내는 현재 기준으로 클라이언트 시각 데이터이므로 서버 공용 chunks_index.bin을 변경하지 않아도 된다.
  • Unity export 후 사람이 diff를 읽고 수정하기 쉽다.
  • 연출 파라미터와 버전을 함께 저장하기 쉽다.
  • 기존 LevelMarker 이름으로 순서를 표현하는 방식은 빠른 실험에는 가능하지만, 누락·중복·정렬 오류에 취약해 정식 구조로는 비추천한다.

좌표 변환

기존 TerrainExtractor와 마찬가지로 Unity world position의 x/y/z를 그대로 기록한다. quaternion도 동일 규칙을 쓸 수 있다.

Y 높이 처리

export한 y를 fallback으로 보존하고, 런타임에 해당 청크가 Ready일 때만 heightAtWorld로 재보정하면 스트리밍 중 0 높이로 떨어지는 문제를 피할 수 있다.

접선과 방향

엔진에서 인접 점 차이로 tangent를 계산한다. 화살표는 tangent와 지형 normal로 회전을 만들고, 구체는 tangent 방향 순차 펄스에 사용한다.

05 · RUNTIME NOTES

연출 품질을 좌우하는 런타임 규칙

표현 방식보다 “경로 전체를 항상 다 그리지 않는 것”과 “플레이어 진행도에 맞춰 앞쪽만 보여주는 것”이 실제 체감 품질에 더 큰 영향을 준다.

공통 권장 규칙

  • 플레이어와 가장 가까운 path sample을 찾아 현재 진행 index로 사용한다.
  • 뒤쪽 2~4m는 빠르게 소거하고, 앞쪽 25~45m만 표시한다.
  • 급회전 구간은 표시 밀도를 높이고 직선은 낮춘다.
  • 카메라 밖·거리 밖 표식은 CPU 단계에서 제출하지 않는다.
  • 지형 위 offset은 구체 약 0.35~0.7m, 바닥 표식 약 0.03~0.08m에서 시작해 튜닝한다.
  • 플레이어가 경로를 크게 벗어나면 가장 가까운 복귀 지점부터 다시 활성화한다.

프로젝트 특화 주의점

  • EnergyOrb drawcall 상한 512: 기존 몬스터 오브와 같은 큐를 공유하면 대규모 전투에서 경쟁한다. 길 안내 전용 버퍼/상한이 안전하다.
  • EnergyOrb bone buffer: 경로 구체에는 불필요하다. 구조를 그대로 쓰면 메모리 업로드와 API가 과도해진다.
  • Forward 계열 파티클: 현재 deferred 경로에서 tonemap 이후 그려져 HDR bloom 기대와 다르다.
  • Terrain streaming: 아직 로드되지 않은 청크의 높이 질의는 0을 반환하므로 authored y fallback이 필요하다.
  • 사용자 검증 대상이 standalone이므로 첫 구현은 반드시 standalone/game.*의 update/render 수명주기에 연결되어야 한다.

최종 제안

구체를 기본 언어로, 화살표를 문장부호로

처음에는 2번 단독으로 구현해 기반을 검증하고, 필요할 때만 급회전·갈림길 checkpoint에 1번 화살표를 얹는 것이 좋다. 둘 다 동일한 path sample과 진행 index를 공유할 수 있어 데이터 파이프라인을 다시 만들 필요가 없다. 반대로 처음부터 두 연출을 동시에 개발하면 미술 튜닝 범위가 커지므로, 설계 단계의 1차 목표는 하나로 제한하는 편이 안전하다.
